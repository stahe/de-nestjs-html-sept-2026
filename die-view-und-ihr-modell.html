    4. Die View und ihr Modell

    Bisher haben die Actions ihre Antworten selbst erzeugt. In einer MVC-Anwendung ist das die Aufgabe einer View: einer Datei, die die HTML-Seite beschreibt, mit Platzhaltern für die Daten, die die Action ihr übergibt – das Modell der View. Wir verwenden die View-Engine [Handlebars] über das Paket [hbs], das sie an [Express] anpasst.

    import { NestFactory } from '@nestjs/core';
import { NestExpressApplication } from '@nestjs/platform-express';
import { join } from 'path';
import { AppModule } from './app.module';

async function bootstrap() {
  // NestExpressApplication: gibt Zugriff auf die Express-spezifischen Methoden
  const app = await NestFactory.create<NestExpressApplication>(AppModule);
  // die Views liegen im Ordner [views] im Wurzelverzeichnis des Projekts;
  // nach der Kompilierung liegt diese Datei in dist/: das Wurzelverzeichnis ist daher '..'
  app.setBaseViewsDir(join(__dirname, '..', 'views'));
  // die View-Engine: Handlebars, bereitgestellt durch das Paket [hbs]
  app.setViewEngine('hbs');
  await app.listen(3000);
  console.log('Server started on http://localhost:3000');
}

    import { Controller, Get, Param, Render, Res } from '@nestjs/common';
import { Response } from 'express';

@Controller()
export class ViewsController {
  // @Render('index'): das von der Action zurückgegebene Objekt ist das MODELL der View
  // views/index.hbs; NestJS ruft die View-Engine selbst auf
  @Get()
  @Render('index')
  home(): object {
    return {
      title: 'My first view',
      message: 'This page was built by Handlebars, on the server.',
      time: new Date().toLocaleTimeString('en-US'),
    };
  }

  // res.render(view, model): die View wird WÄHREND der Ausführung der Action gewählt
  @Get('hello/:name')
  hello(@Param('name') name: string, @Res() res: Response): void {
    if (name === 'unknown') {
      res.status(404).render('unknown', { name });
      return;
    }
    res.render('index', {
      title: `Hello ${name}`,
      message: 'This time, the view was chosen by res.render.',
      time: new Date().toLocaleTimeString('en-US'),
    });
  }
}

    Kommentieren wir diesen Code:

    • Zeile 9: [{{!-- ... --}}] ist ein Kommentar ([Handlebars]): Er erscheint nicht auf der erzeugten Seite (anders als ein HTML-Kommentar wie [<!-- -->]);
    • Zeile 10: Eine im Modell fehlende Variable ([nonexistent]) erzeugt einen leeren String, ohne Fehler;
    • Zeilen 12–13: [{{html}}] maskiert die Sonderzeichen in HTML ([<] wird zu [&lt;] ...): Der Text wird unverändert angezeigt. [{{{html}}}] (drei geschweifte Klammern) wird ohne Maskierung eingefügt: Es wird als HTML interpretiert. Dreifache geschweifte Klammern werden nur für HTML verwendet, das von der Anwendung erzeugt wurde, niemals für Benutzereingaben: Ein Benutzer könnte HTML oder sogar [JavaScript] in die Seite einschleusen (ein sogenannter [XSS]-Angriff);
    • Zeilen 15–19: [{{#if}}] / [{{else}}] / [{{/if}}]: ein bedingter Block. Die Bedingung ist ein Wert aus dem Modell, kein Ausdruck: [false], [undefined], [null], [''], [0] und das leere Array gelten als falsch;
    • Zeilen 20–22: [{{#unless}}] ist das Gegenteil von [{{#if}}];
    • Zeilen 26–32: [{{#each}}] wiederholt seinen Inhalt für jedes Element eines Arrays. Innerhalb des Blocks ist der Kontext das aktuelle Element: [{{name}}] ist der Name des aktuellen Produkts. Es stehen spezielle Variablen zur Verfügung: [@index] (Position, bei 0 beginnend), [@first], [@last]. [../currency] verweist auf den übergeordneten Kontext, [@root.name] auf das Wurzelmodell;
    • Zeile 36: Ein [{{else}}] innerhalb eines [{{#each}}] behandelt den Fall eines leeren Arrays;
    • Zeilen 39–41: [{{#with}}] wechselt den Kontext; es kann auch ein relativer Pfad verwendet werden (Zeile 42).

    import { NestFactory } from '@nestjs/core';
import { NestExpressApplication } from '@nestjs/platform-express';
import { NextFunction, Request, Response } from 'express';
import * as hbs from 'hbs';
import { dirname, join } from 'path';
import { AppModule } from './app.module';

const ROOT = join(__dirname, '..');

async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule);

  // 1. statische Dateien: public/css/styles.css wird als /css/styles.css ausgeliefert
  app.useStaticAssets(join(ROOT, 'public'));
  // Bootstrap wird direkt aus node_modules ausgeliefert, unter /bootstrap/
  app.useStaticAssets(join(dirname(require.resolve('bootstrap/package.json')), 'dist'), { prefix: '/bootstrap/' });

  // 2. die Views; views/layout.hbs ist das Layout ALLER Seiten
  app.setBaseViewsDir(join(ROOT, 'views'));
  app.setViewEngine('hbs');
  // 3. die Partials: views/partials/xxx.hbs wird mit {{> xxx}} eingefügt
  await new Promise<void>((done) => hbs.registerPartials(join(ROOT, 'views', 'partials'), () => done()));

  // 4. eine Express-Middleware: was sie in res.locals ablegt, wird
  //    dem Modell JEDER View hinzugefügt
  app.use((req: Request, res: Response, next: NextFunction) => {
    res.locals.path = req.path;
    res.locals.year = new Date().getFullYear();
    next();
  });

  await app.listen(3000);
  console.log('Server started on http://localhost:3000');
}

bootstrap();

    Gehen wir diesen Code im Einzelnen durch:

    • Zeile 14: [useStaticAssets] liefert statische Dateien aus einem Ordner aus: Die Datei [public/css/styles.css] wird unter der URL [/css/styles.css] unverändert ausgeliefert, ohne einen Controller zu durchlaufen;
    • Zeile 16: Das CSS-Framework [Bootstrap] wird direkt aus dem Ordner [node_modules] unter dem Präfix [/bootstrap/] ausgeliefert. [require.resolve] findet den Ordner des Pakets [bootstrap], wo auch immer es installiert ist (hier in [examples/node_modules]);
    • Zeile 22: Die Dateien im Ordner [views/partials] werden zu Partial-Dateien: [partials/navbar.hbs] wird mit [{{> navbar}}] in eine View eingefügt. [registerPartials] liest den Ordner asynchron: Wir warten, bis das Lesen beendet ist (die als zweites Argument übergebene Funktion wird am Ende aufgerufen), bevor wir den Server starten;
    • Zeilen 26–30: eine [Express]-Middleware, die vor jeder Anfrage ausgeführt wird. Was sie in [res.locals] ablegt, wird dem Modell jeder View hinzugefügt. So stellen wir allen Seiten gemeinsame Informationen (hier den angeforderten Pfad und das Jahr) bereit, ohne sie in jeder Action zu wiederholen.

    import { HelperOptions } from 'handlebars';

// das Modul 'hbs' hat keine Typdeklarationen: wir beschreiben, was wir davon verwenden
interface Hbs {
  registerHelper(name: string, fn: (...args: any[]) => unknown): void;
  handlebars: { SafeString: new (html: string) => unknown; escapeExpression(text: string): string };
}

export function registerHelpers(hbs: Hbs): void {
  // {{uppercase name}}: ein einfacher Helper mit einem Argument
  hbs.registerHelper('uppercase', (text: unknown) => String(text ?? '').toUpperCase());

  // {{#if (eq a b)}}: als Subexpression verwendet, in runden Klammern
  hbs.registerHelper('eq', (a: unknown, b: unknown) => a === b);

  // {{active path '/products'}}: "active", wenn die aktuelle Seite unter diesem Pfad liegt

    typeof path === 'string' && typeof prefix === 'string' && path.startsWith(prefix) ? 'active' : '',

  // Parameter, options.data.root das vollständige Modell der Seite (einschließlich res.locals)
  hbs.registerHelper('money', (amount: unknown, options: HelperOptions) => {
    const currency = options.hash.currency ?? 'EUR';
    const language = options.data?.root?.lang ?? 'en-US';
    return new Intl.NumberFormat(language, { style: 'currency', currency: currency }).format(Number(amount));
  });

  // {{date when}}: ein Datum im Format der Sprache der Seite
  hbs.registerHelper('date', (when: unknown, options: HelperOptions) => {
    const language = options.data?.root?.lang ?? 'en-US';
    return new Intl.DateTimeFormat(language, { dateStyle: 'full' }).format(new Date(String(when)));
  });

  // {{badge stock}}: ein Helper, der HTML erzeugt. SafeString weist
  // Handlebars an, es NICHT zu escapen; der Helper muss dann selbst
  // die Daten escapen, die er darin einfügt (escapeExpression)
  hbs.registerHelper('badge', (stock: unknown) => {
    const n = Number(stock);
    const cssClass = n > 0 ? 'text-bg-success' : 'text-bg-danger';
    const text = hbs.handlebars.escapeExpression(n > 0 ? `${n} in stock` : 'sold out');
    return new hbs.handlebars.SafeString(`<span class="badge ${cssClass}">${text}</span>`);
  });
}

export type Errors = Record<string, string>;

export async function validateForm<T extends object>(
  cls: ClassConstructor<T>,
  body: Record<string, unknown>,
): Promise<{ dto: T; errors: Errors }> {
  // 1. empfangenes Objekt -> Instanz der Klasse (@Transform / @Type werden angewendet)
  const dto = plainToInstance(cls, body);
  // 2. Prüfung aller Constraints
  const violations = await validate(dto);
  // 3. wir behalten die erste Meldung jedes ungültigen Feldes
  const errors: Errors = {};
  for (const v of violations) {
    errors[v.property] = Object.values(v.constraints ?? {})[0];
  }
  return { dto, errors };
}

    4.7.1. Validierung durch den Browser

    Die Attribute [required], [maxlength], [min], [max], [type="email"] ... weisen den Browser an, das Formular vor dem Absenden zu validieren: Der Benutzer wird sofort über einen Tooltip benachrichtigt, ohne jegliche Kommunikation mit dem Server. Dieses Verhalten wird durch den Link „aktivieren“ ([/register?html5=1]) ausgelöst, der das Attribut [novalidate] aus dem Formular entfernt.

    Diese Validierung ist eine Komfortfunktion, keine Sicherheitsmaßnahme: Man kann sie umgehen, indem man einfach das Attribut [required] mit den Entwicklerwerkzeugen des Browsers entfernt oder die Anfrage mit [curl] sendet. Die serverseitige Validierung bleibt unverzichtbar. Deshalb deaktiviert das Beispiel die Browser-Validierung standardmäßig: um die Funktionsweise des Servers zu demonstrieren. Die Fallstudie behält jedoch beides bei: die HTML5-Attribute für den Komfort und die serverseitige Validierung für die Sicherheit.

    4.8. Beispiel 20: Das Post/Redirect/Get-Muster

    Wenn ein POST-Formular erfolgreich gesendet wurde, kann die Action direkt eine Seite anzeigen. Das Problem entsteht, wenn der Benutzer diese Seite anschließend aktualisiert (Taste F5): Der Browser sendet das Formular erneut, und die Operation wird ein zweites Mal ausgeführt (eine doppelt aufgegebene Bestellung, ein doppelt vereinbarter Termin ...). Das Muster Post / Redirect / Get (PRG) verhindert dieses Problem: Eine erfolgreiche POST-Action erzeugt keine Seite, sondern leitet auf eine GET-Seite weiter. Das Neuladen dieser Seite sendet nur die GET-Anfrage, die keine Auswirkung hat.

    Ein Detail bleibt: Die GET-Seite muss eine Meldung anzeigen („Die Aufgabe wurde hinzugefügt“), obwohl diese Meldung von der POST-Action in einer anderen Anfrage erzeugt wurde. Sie wird in einem kurzlebigen Cookie übertragen, das von der nächsten Anfrage gelesen und gelöscht wird: Das ist eine Flash-Meldung.

    import { NextFunction, Request, Response } from 'express';

const FLASH_COOKIE = 'flash';

// speichert eine Meldung, die von der NÄCHSTEN Seite angezeigt wird, und zwar nur einmal
export function flash(res: Response, message: string): void {
  res.cookie(FLASH_COOKIE, message, { httpOnly: true, sameSite: 'lax', maxAge: 60_000 });
}

// bei jeder Anfrage: die ausstehende Meldung wandert vom Cookie nach res.locals (also
// ins Modell der View), und das Cookie wird gelöscht
export function flashMiddleware(req: Request, res: Response, next: NextFunction): void {
  res.locals.flash = req.cookies?.[FLASH_COOKIE] ?? null;
  if (res.locals.flash) {
    res.clearCookie(FLASH_COOKIE);
  }
  next();
}

    // Bestätigung der Formulare mit dem Attribut data-confirmation="..."
// Ohne JavaScript werden diese Formulare einfach ohne Bestätigung gesendet.
(() => {
  const modal = document.getElementById('confirmation-modal');
  const message = document.getElementById('confirmation-modal-message');
  let pending = null; // das Formular, das gesendet wird, wenn der Benutzer bestätigt

  // 1. wir fangen das Absenden der zu bestätigenden Formulare ab
  document.querySelectorAll('form[data-confirmation]').forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault(); // das Absenden wird angehalten
      pending = form;
      message.textContent = form.dataset.confirmation;
      modal.classList.remove('d-none'); // das Fenster erscheint
    });
  });

  // 2. die beiden Buttons des Fensters
  modal.addEventListener('click', (event) => {
    const action = event.target.dataset.action;
    if (action === 'yes') {
      pending.submit(); // Absenden, OHNE das Ereignis 'submit' erneut auszulösen
    } else if (action === 'no') {
      modal.classList.add('d-none');
      pending = null;
    }
  });
})();
    • Zeile 3: Der Code ist in eine Funktion eingebettet, die sofort ausgeführt wird, um keine globalen Variablen anzulegen;
    • Zeilen 9–16: Das Absenden jedes Formulars mit dem Attribut [data-confirmation] wird abgefangen. [preventDefault()] setzt das Absenden aus; das Formular wird gespeichert, die Frage wird im Fenster platziert ([textContent], nicht [innerHTML]: Die Frage wird als Text angezeigt und niemals als HTML interpretiert), und das Fenster wird angezeigt;
    • Zeilen 19–27: „Ja“ sendet das zwischengespeicherte Formular ab. Die Methode [submit()] eines Formulars sendet es ab, ohne das Ereignis [submit] auszulösen: Es erscheint also keine erneute Bestätigungsabfrage. „Nein“ blendet das Fenster aus.

    Ist [JavaScript] deaktiviert, werden die Formulare einfach ohne Bestätigung abgesendet: Die Anwendung funktioniert weiterhin. Das ist das Prinzip der schrittweisen Verbesserung: [JavaScript] bietet zusätzlichen Komfort, ist aber nicht unverzichtbar.
